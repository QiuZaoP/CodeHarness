# 任务生命周期与调度

## 后台执行

`POST /api/v1/tasks/{taskId}/run` 只负责原子获取任务租约并把任务交给进程内执行器，成功时
返回 `202 Accepted`，不会等待任务完成。客户端通过任务查询或 SSE 获取后续状态。

同一任务在任何时刻只能有一个有效租约。租约保存在 SQLite `task_leases` 表中，抢占使用
单条条件写入；未过期租约不能被其他 Runner 或重复 `run` 覆盖。执行器定期续租，同时轮询
持久化的控制请求。正常完成、失败、暂停和取消后都会按 owner 释放租约。

当前队列是单进程内调度，不保证任务优先级或跨进程主动唤醒。SQLite 租约保证多实例不会
同时执行同一任务；另一个实例发出的暂停/取消请求由当前 Runner 在轮询周期内观察。

## 控制语义

| 操作       | 前置状态                   | 结果                                       |
| ---------- | -------------------------- | ------------------------------------------ |
| `run`      | `CREATED`                  | `202`；后台进入前检查、规划和执行          |
| `pause`    | 已获得租约的运行态         | 取消当前操作，进入 `PAUSED` 并保存恢复目标 |
| `resume`   | 有恢复目标的 `PAUSED`      | `202`；抢占新租约并从保存的阶段继续        |
| `cancel`   | 允许取消的非终态           | 终止当前操作并进入 `CANCELLED`             |
| `apply`    | `READY_FOR_REVIEW`         | 进入 `APPLIED`                             |
| `rollback` | 非运行态且状态允许转为取消 | 验证并恢复基线工作区，然后进入 `CANCELLED` |

暂停和取消先持久化 `controlRequest` 与审计，再通过本地 `AbortController` 立即通知当前
Runner；非本地 Runner 会在控制轮询时观察。工具和命令完成协作式清理后才释放工作区写锁和
任务租约，因此不会在旧进程树仍运行时启动恢复任务。

恢复目标只允许：

- `CREATED`、`PRECHECKING`、`PLANNING` 恢复到 `PLANNING`；
- `EXECUTING` 恢复到 `EXECUTING`；
- `VERIFYING` 恢复到 `VERIFYING`。

`resumeStatus` 和 `controlRequest` 是内部持久化字段，不出现在公共 Task DTO。暂停产生
`task.paused`，恢复产生 `task.resumed`；控制请求本身只写审计，不发布伪状态事件。

当前 `apply` 只完成已审阅任务的生命周期确认。把 Diff 应用到目标仓库、文件级接受/拒绝
和最终交付检查属于后续变更交付阶段；本阶段不会修改项目源目录。

## 重启恢复

应用启动时检查 `CREATED/PRECHECKING/PLANNING/EXECUTING/VERIFYING`：

- 没有租约的普通 `CREATED` 任务保持不变；
- 存在有效租约的任务视为仍由其他实例负责；
- 租约缺失或过期的中断运行转为 `PAUSED`，保存确定的恢复目标；
- 已持久化取消请求的中断运行转为 `CANCELLED`；
- 后台恢复扫描会继续观察启动时尚有效、之后停止续租的租约；
- 过期租约被清理，恢复过程写状态事件和审计。

服务正常关闭会向本进程内活动任务发送暂停信号并等待清理，之后才关闭数据库。

## 配置

| 环境变量               | 默认值  | 说明                   |
| ---------------------- | ------- | ---------------------- |
| `TASK_LEASE_TTL_MS`    | `15000` | 租约有效期             |
| `TASK_CONTROL_POLL_MS` | `250`   | 续租及远端控制轮询周期 |

轮询周期应明显小于租约有效期。后续引入外部队列时仍保留 SQLite 租约作为最终并发门禁。
